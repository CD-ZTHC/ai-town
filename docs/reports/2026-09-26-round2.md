## 二、做了什么

### 1. 接入 pi-ai（`LLM_PROVIDER=pi`）

新增 `server/llm-pi.js`，实现了第一轮抽出来的 provider 接口。模型名有两种写法：

- **`MODEL=anthropic/claude-sonnet-5`**：写成「服务商/模型」，走 pi-ai 内置的服务商。密钥由 pi-ai 从各家自己的环境变量读取（`ANTHROPIC_API_KEY` 等）。
- **`MODEL=glm-5.3`**：不带前缀，仍然走 `BASE_URL` / `API_KEY` 指向的网关，由 pi-ai 的 `openai-completions` 实现发请求。请求里和默认实现一样带上 `reasoning_effort: low` 和 `response_format`。
- `MODEL` / `MODEL_FAST` / `MODEL_SMART` 三档可以混用不同的服务商。

**与 `llm.js` 的分工**：

- pi-ai 遇到请求失败时不抛异常，而是返回一条 `stopReason: "error"` 的消息。适配器把它转成异常，并保留上游的状态码和原文（例如 `429: …请求频率过高…`）。这样 `llm.js` 原有的逻辑照常生效：限流时退避、鉴权失败不重试、网关不支持 JSON 模式时自动关掉。
- 关掉了 pi-ai 和各家 SDK 自带的重试（`maxRetries: 0`）。重试、限流、预算仍然只由 `llm.js` 负责，不会叠加重试。

**安装与部署**：

- `package.json` 里用 `optionalDependencies` 精确锁定 0.87.1，并提交了 `package-lock.json`。
- 没装 pi-ai 时，启用 `pi` 会给出明确的安装提示；不启用则完全不受影响。
- pi-ai 连带的依赖（OpenAI、Anthropic、Google、AWS 的 SDK）约 89MB，所以 Docker 镜像默认不装，需要时用 `--build-arg WITH_PI=1` 构建。

**验证**（`test/llm-pi.test.js`）：

- 用一个本地的假网关模拟真实网关（流式 SSE 返回），测试请求体、鉴权、用量统计、错误映射，以及接进 `llm.js` 后的端到端调用和 JSON 模式降级。
- 内置服务商的路由用 pi-ai 自带的 faux provider 测试。
- 文档里的示例模型名都在 pi-ai 的模型目录里核对过。原来写的 `deepseek-chat` 目录里没有，已改成 `deepseek-flash`。

### 2. 结构化输出（`LLM_JSON_SCHEMA=1`）

- `chatJSON` 新增 `schema` 选项。开启后，请求里的 `response_format` 从 `json_object` 换成 `json_schema`（非严格模式，只支持部分 JSON Schema 的网关也能用）。
- 世界架构师的输出定义为 `ARCHITECT_SCHEMA`：要么是一份补丁，要么是一条能力缺口；补丁里的操作名只能从架构师可用的操作里选。
- 网关不支持 `json_schema` 时，自动退回 `json_object`，之后不再发送 schema。

### 3. AI 表现指标

- 新增 `server/sim/metrics.js`。计数按游戏日保存进存档（保留 30 天）；过去的日子只保留计数，不保留明细。
- `GET /api/metrics` 返回完整数据；`/api/usage` 附带主要指标；AI 大脑面板显示赴约率、重复率和 JSON 修复/失败率。

| 指标 | 怎么算 |
| --- | --- |
| 约定兑现率 | 按「居民 + 日程条目」计：到点真的到场才算兑现；同一个约定重复约只算一次；还没到时间的不算失约 |
| 对话重复率 | 同一对人两天内的上一次对话，摘要的双字组相似度 ≥ 0.5 算重复；兜底台词不参与 |
| 剧情线程回收率 | 已回收的线程数 / 全部线程数（另外统计推进过的比例） |
| JSON 修复率 / 失败率 | 按模块统计：第一次输出不是合法 JSON、要求重写一次的比例；重写后仍然失败的比例 |
| 兜底率 | 规划和对话里，没用上模型输出、改用规则兜底的比例 |

用录制回复跑 7 个游戏日的结果：赴约 89%、对话重复 17%、JSON 失败 0。

### 4. 存储

我先实测了存档和快照各自占多少，再决定怎么改：

- `save.json` 的每一项都有上限（每人记忆 400 条、日志 400 条、对话 120 条），跑 20 天稳定在约 1.1MB。一次存档的开销是序列化 1.8ms 加写盘 0.3ms。
- 真正的大头是**每小时的完整快照**：保留 24 份，每份最多约 1MB，合计约 24MB。

**做法**：

- 快照改用 gzip 压缩存储，文件名变为 `dNNN-HH.json.gz`，大小约为原来的 13%。
- 仍然同步写入：每游戏小时一次，每次压缩约 4ms，不值得为此引入异步写入的复杂度。
- 升级前留下的 `.json` 旧快照仍然可以列出、回溯和分叉；同一整点写入新快照时，会删掉旧格式的那份。

**没有把存档改成 `node:sqlite` 增量存储**。回溯、时间线分叉、`evolve`、Mod 导出都依赖单文件存档，改造成本高，而换来的只是每次存档省下约 2ms。`node:sqlite` 用在了真正需要增量写入的地方：下一节的向量缓存。

### 5. 记忆压缩与可选的 embedding

**压缩**：

- 每人最多 400 条记忆。满了以后，不再直接删掉最旧的一条琐事，而是把**最早一天的琐碎记忆**合并成一条摘要，一次腾出好几个位置。
- 反思、日记、已有的摘要和重要记忆（重要性 ≥ 6）不参与合并。

**每晚整理**：

- 写完日记后，记忆超过 300 条的居民，会把前天以前最早的一天交给快模型，浓缩成一条第一人称的摘要。
- 模型调用失败，或者没有配置模型时，改用规则摘要。

**Embedding**（配置 `EMBED_MODEL` 后启用）：

- 调用 OpenAI 兼容的 `/embeddings` 接口。算出的向量按「模型 + 文本」缓存在 `data/embeddings.db`（`node:sqlite`），重启后不用重算。
- 检索时，相关性取双字组相似度和语义相似度中较高的一个。
- 最多等 `EMBED_TIMEOUT_MS`（默认 4 秒）；超时或出错时，这一次只用双字组。
- **没有配置时，提示词与之前逐字相同。**

**实测**：用录制回复跑 20 个游戏日，每位居民的记忆稳定在 320 到 390 条，较早的日子都变成了摘要（大部分由模型整理，其余是规则摘要）。

### 6. 前端拆分（先加测试，再拆）

1. **先加测试**：给不碰 DOM 的纯函数加了测试（`test/frontend.test.js`），覆盖噪声、颜色、天色、坐标换算与点击命中、转义、时间格式、张力曲线、居民状态卡。
2. **写了 `tools/browser-check.js`**（`mise run browser-check`）：零依赖，直接用 Chrome DevTools 协议驱动本机的无头 Chrome。它依次打开检查器、故事、建设、日报、关系网、事件、说明、天气、AI 大脑，再进入沉浸模式、填角色卡、进入游戏模式，同时收集控制台错误并截图。先在拆分前的代码上跑一遍作为基准。
3. **拆 `render.js`**：和第一轮拆 `sim.js` 的做法一样，方法原样搬进各个模块，再挂回 Renderer。新旧 51 个方法源码逐一一致，48 行常量和工具函数一致。
4. **拆 `ui.js`**：共用状态放进 `ui/core.js`，其中 `app` 改为 live binding（`export let app` + `setApp`），各模块里原有的 `app` 写法不用改。唯一改动的一行是 `init` 里的 `app = a` 改为 `setApp(a)`。38 个导出和 77 个顶层定义都与原来一致。拆分脚本会检查「在别的模块里给模块级 `let` 变量赋值」的情况，发现就中止，因为拆开后这种写法会出错。
5. 每一步拆完，无头 Chrome 检查都没有错误，截图也与基准一致。

## 三、顺带发现并修复的原有 bug

| Bug | 怎么发现的 | 影响 |
| --- | --- | --- |
| Dock 按钮被重复绑定（`ui.js` 与 `hud.js` 各绑了一次） | 无头 Chrome 检查 | 天气菜单点一下就开了又关，**完全打不开**；日报、关系网、建设面板每次都请求两次数据，关系网还会启动两个动画循环 |
| Dock 里的天气菜单展开到屏幕外 | 修好上一条后看截图 | 菜单仍按「按钮下方」定位（按钮原来在顶栏），1400×813 的窗口里菜单顶部在 y=803，几乎整个看不见。现在下方放不下时改为向上展开；检查脚本也会断言菜单完整地在屏幕内 |
| 世界架构师的补丁常因「未知地点：undefined」被拒 | **你用真实模型录制的回复** | 4 份录制回复里有 3 份把选址写成了 `args.near`（应为 `args.place.near`），带着错误修正一轮后模型往往还是同样的写法。现在接受这种简写，选到的位置与完整写法相同；不存在的地点仍会被拒绝 |

自己写代码时被测试拦下、已在提交前修好的两个问题（这里如实列出）：

- **约定兑现的统计**：一开始计数时没有区分居民，两个人约了同一件事只能算一次到场。回放测试里赴约率显示为 27%，这个数字不合理，我据此查出了问题；修正后是 89%。
- **Embedding 出错时的返回值**：出错时 `ensure()` 会返回「成功」，因为错误被吞掉以后 `Promise.all` 仍然正常结束。修正后，每批请求都返回明确的成功或失败标记。
