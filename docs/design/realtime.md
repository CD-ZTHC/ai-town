# 低延迟与无锁定战斗

> 状态：R0～R4 已实施（2026-10-04，分支 `feat/realtime`，见第 11 节）；线上默认 `REALTIME=off`，需要在后台设置里打开。
> 决策（已确认）：
> 1. 线上经 **Cloudflare** 代理，源站由 Caddy（`/root/site/Caddyfile`）反向代理到 `localhost:3003`；**不暴露源站 IP**，也不另做源站加固。
> 2. 电脑上允许**鼠标瞄准**。
> 3. 玩家自己的移动**由客户端决定、服务器校验**。
> 4. 战斗改为**无锁定**：靠方向和判定区域命中，能靠走位躲开。

## 1. 现状与延迟从哪来

代码里的关键数字（2026-10-03 核对）：

| 项 | 现在 |
|---|---|
| 世界快照推送 | `TICK_HZ` 默认每秒 4 次（SSE） |
| 走路 | 每次一个 `POST /api/avatar/goto`（目标格子，服务器寻路）；前端最多 280 毫秒发一次，服务器 250 毫秒内只收一次 |
| 出招 | 每次一个 `POST /api/avatar/act` |
| 其他单位的位置 | 在相邻两次快照之间插值，再叠一层指数平滑 |
| 自己的位置 | 和别人一样来自快照 |
| 传输路径 | 浏览器 → Cloudflare → Caddy（`encode zstd gzip`）→ Node |

按「Cloudflare 往返 200 毫秒以上」估算，按下方向键到自己的小人动起来：

| 环节 | 估算 |
|---|---|
| 前端节流，等能发下一次请求 | 0～280 ms |
| 请求经 Cloudflare、Caddy 到达服务器 | ≈ 100 ms+ |
| 服务器走位后等下一次快照 | 平均 ≈ 125 ms |
| 快照经 Caddy、Cloudflare 推回浏览器 | ≈ 100 ms+ |
| 前端插值与平滑 | ≈ 150～250 ms |
| **合计** | **≈ 0.5～0.9 秒** |

结论：最大的问题是**自己的小人也要等服务器**，其次才是传输。玩家若主要在中国大陆，Cloudflare 普通网络的往返 200 ms 以上是物理下限，服务器改不掉，所以方案的重点是**让玩家感觉不到延迟**。

## 2. 目标

| 指标 | 目标 |
|---|---|
| 按键 → 自己的小人移动 | ≤ 1 帧（≈ 16 ms） |
| 按键 → 出招动作、读条、范围提示出现 | ≤ 1 帧 |
| 出招 → 伤害数字（服务器确认） | ≤ 往返时间 + 50 ms |
| 战斗中其他单位的移动 | 顺滑无跳动，延后 ≈ 100 ms 播放 |
| 校验回弹 | 正常游玩几乎不出现（< 1 次 / 10 分钟） |
| 战斗时每位观众的下行带宽 | ≤ 8 KB/s（增量编码后） |

## 3. 传输

### 3.1 WebSocket 经 Cloudflare
- Cloudflare 所有套餐都能代理 WebSocket，Caddy 的 `reverse_proxy` 也会自动转发 WebSocket 升级请求，**源站 IP 不暴露、Caddy 配置不用改**。
- 新接口 `GET /api/realtime`（升级为 WebSocket），同一条连接承载：
  - 上行：移动上报、出招、心跳、延迟探针；
  - 下行：战斗通道（第 6 节）、即时事件（`combat`、`stage` 等）。
- 世界快照、日志、面板类推送仍走现有的 SSE（低频、不影响手感），以后再视情况并入。
- Cloudflare 会关闭约 100 秒没有数据的连接：每 20 秒心跳一次；断线指数退避重连。
- **兜底**：WebSocket 连不上（被网络环境拦截等）时，退回现在的「SSE 下行 + HTTP 上行」，功能不变、只是慢一些。

### 3.2 消息格式
- JSON，单字母字段名控制体积；每条消息带类型 `t` 与序号 `s`。
- 上行：`{t:'mv', s, x, y, d, ts}`（移动）、`{t:'act', s, skill, ax, ay}`（出招，`ax/ay` 为瞄准方向）、`{t:'ping', ts}`。
- 下行：`{t:'pong', ts}`、`{t:'ack', s, x, y}`（移动纠正，只在回弹时发）、`{t:'fx', …}`（战斗通道）、`{t:'ev', name, data}`（即时事件）。
- 身份沿用现有的会话 Cookie（升级请求带 Cookie），与 HTTP 接口的权限判断一致。

### 3.3 Caddy 与压缩
- 服务器推送已带 `Cache-Control: no-cache, no-transform` 与 `X-Accel-Buffering: no`。Caddy 的 `encode zstd gzip` 对推送流是否会攒包，R0 实测（逐跳 `curl -N` 观察到达间隔）。
- 若确认有缓冲：在 `town.zthc.net` 里把 `/api/stream`、`/w/*/api/stream`、`/api/realtime` 排除在 `encode` 之外（需要改 Caddyfile，由你确认后执行）。

## 4. 自己的移动：客户端决定、服务器校验

### 4.1 客户端
- 每帧用本地的可走格子（`app.regionWorlds[区域].walk`）计算自己的位置：
  - 键盘：WASD 合成方向，按 `SPEED`（4 格/秒）移动；撞墙时沿墙滑动；
  - 手机：摇杆直接给方向和力度（不再「找一格再寻路」）；
  - 点地面走路：本地寻路后沿路径走。
- 自己的小人只用本地位置画；收到服务器纠正（`ack`）时平滑对齐，偏差大于 2 格时直接跳过去。
- 约每 100 毫秒上报一次位置（有变化时），停下时立即补一次。

### 4.2 服务器校验（`server/avatars.ts`）
- **速度**：距离 ≤ `SPEED × 间隔 × 1.2 + 0.3` 格；
- **地形**：两次上报之间的连线沿途的格子都要能走（不穿墙、不穿水）；
- **地图**：不能跨地图；跨地图只能在路口发生（到达路口格后由服务器切换，同现在的 `hop`）；
- **状态**：被打倒、被击退、闪避冲刺这类服务器决定的位移，服务器先下发，客户端对齐后再上报。
- 不通过 → 位置停在上一个合法点，回一条 `ack` 让客户端回弹，并计一次异常；一分钟内异常超过 10 次 → 这个化身退回「服务器决定位置」模式（现有的 goto），直到重新进入游戏模式。
- 其他观众看到的化身位置仍来自服务器（通过校验的位置）。

## 5. 无锁定战斗

### 5.1 操作
| 操作 | 电脑 | 手机 |
|---|---|---|
| 移动 | WASD | 摇杆 |
| 瞄准 | 鼠标指向的方向 | 摇杆方向 / 最后的移动方向，带吸附 |
| 普攻 | 左键 / J | 攻击按钮 |
| 闪避 | 右键 / K（朝移动方向；没在移动时朝鼠标） | 闪避按钮 |
| 技能 | 1～4（朝鼠标） | 技能按钮 |
| 聊天 | 走近按 E / 点头像栏 | 💬 |

- **战斗姿态**：身边 6 格内有可攻击的敌人，或者已经在打时进入。此时左键是攻击、鼠标变成准星、脚下显示淡淡的朝向扇形，右键菜单被屏蔽。平时左键仍是点地走路、点居民聊天。
- **手机吸附**：出招方向前方 ±30° 内有敌人时，朝最近的那个偏过去。

### 5.2 招式 = 判定区域
- 出招时带瞄准方向 `(ax, ay)`；判定区域以出手的人为原点、朝瞄准方向展开。现有四种形状沿用：
  - `single`：改为面前一小段扇形（近战挥砍，半径 = range，角度 ±35°）；
  - `cone` / `circle`：照旧，以瞄准方向为准；
  - `line`：改为**弹道**——一个以 `range / 飞行拍数` 的速度飞行的判定点，沿途第一个敌人被打中（`radius` 为宽度），能被躲开、被墙挡住。
- 生效时打中区域里所有的敌对单位（可能打空，也可能打中多个）；同伴不受伤害。
- 不需要先「进入战斗」：打中可攻击的单位才自动开战（谁能被打的规则不变）。
- **世界包数据不用改**：`combat` 块的 windup / recover / range / shape / radius / cd 含义不变；AI 架构师写的招式照样能用。

### 5.3 能躲开
- 敌人蓄力时下发攻击范围（`{from, aim, shape, range, radius, until}`），地上画红色区域并随蓄力填满；生效时按**那一刻**的位置判定。
- 闪避的无敌帧保留。
- 每拍 0.25 秒：蓄力 ≥ 2 拍的招式有 ≥ 0.5 秒的躲闪窗口，扣掉下行延迟约剩 0.3～0.4 秒。若实测不够灵敏：引擎内部改为每 0.1 秒结算一次，「拍」仍作为数据单位（世界包不用改）。

### 5.4 公平性
- **玩家打别人**：服务器回溯到玩家出招时看到的位置做判定（每个单位保留最近 1 秒的位置历史；回溯量 = 测得的单程延迟 + 插值延后，上限 250 ms）。
- **别人打玩家**：用玩家上报的位置判定——本地已经躲开、并及时上报的就算躲开。
- 规则 AI：仍在内部选目标，按目标当前位置瞄准；弹道类稍微预判。居民、怪物同样可能打空、被躲开。战术、台词、旁观者加入、演出不受影响。

### 5.5 本地先播放
- 按下技能：立即播放起手动作、读条、自己的范围提示；服务器的 `cast` 到达后只对齐时间。
- 伤害数字、命中火花、受击闪白以服务器为准（晚一个往返）；本地可以先播「挥空」的音效与轨迹，命中效果等确认。

## 6. 战斗通道（下行）
- 只在视野内（同一地图、镜头附近）有战斗时，经 WebSocket 每秒推 15 次：参战单位的位置、血量、读条、状态、弹道。
- 增量编码：只发变化了的字段；单位用短 id。
- 其他单位按「服务器时间 − 100 ms」插值播放（缓冲两帧，网络抖动时不跳）。
- 世界快照仍每秒 4 次，战斗通道里的单位以战斗通道为准。

## 7. 测量（R0）
- 延迟探针：前端每 5 秒发一次 `ping`（WebSocket，没有时用 HTTP），记录往返时间；调试面板（`?debug=net`）显示 p50 / p95 / 抖动。
- 推送到达间隔：前端统计快照、战斗通道消息的到达间隔分布，判断是否被缓冲攒包。
- 后台概览新增「网络」小卡：按世界的在线人数、往返时间 p50 / p95、回弹次数。
- 逐跳检查：源站本机 → Caddy → Cloudflare 三处分别 `curl -N` 推送流，对比到达间隔，定位缓冲发生在哪一层。

## 8. 兼容与上线
- 设置项 `REALTIME`：`off`（现状）/ `move`（只开本地移动）/ `on`（本地移动 + 无锁定战斗 + 战斗通道），默认先 `off`，线上灰度后再改默认。
- 旧的 `/avatar/goto`、`/avatar/act` 保留：旧版页面、WebSocket 不可用时照常工作；`act` 没给瞄准方向时，朝最近的敌人（等同现在的行为）。
- 存档与世界包格式不变。

## 9. 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| R0 测量 | 延迟探针、到达间隔统计、逐跳检查、后台网络卡片 | 拿到线上往返时间 p50 / p95；确认缓冲发生在哪一层 |
| R1 本地移动 | 客户端移动（键盘 / 摇杆 / 点地）、位置上报（先走 HTTP）、服务器校验与回弹、异常退回 | 按键到画面移动 ≤ 1 帧；正常游玩无回弹；作弊式上报被拦下（测试） |
| R2 无锁定战斗 | 鼠标瞄准与战斗姿态、判定区域、弹道、范围预警、本地先播、延迟补偿、手机吸附 | 能靠走位躲开 Boss 招式；打中与否和画面一致；规则测试覆盖判定与回溯 |
| R3 WebSocket | `/api/realtime`、心跳与重连、HTTP 兜底；移动与出招改走它 | 上行往返时间明显下降；断线自动恢复 |
| R4 战斗通道 | 每秒 15 次增量推送、延后 100 ms 插值 | 战斗中其他单位顺滑；带宽 ≤ 8 KB/s/人 |

R1 收益最大、风险最小，最先做。R3 需要线上验证 Cloudflare、Caddy 对 WebSocket 的转发（预计开箱即用）。

## 10. 风险
| 风险 | 缓解 |
|---|---|
| 客户端决定移动 → 作弊走得快 | 速度、地形、地图三重校验 + 异常退回；休闲游戏，收益有限 |
| 回溯判定让被打的人觉得「明明躲开了」 | 回溯上限 250 ms；范围预警给足躲闪窗口 |
| WebSocket 被某些网络拦截 | 自动退回 SSE + HTTP |
| 下行推送频率提高 → 服务器负载、带宽 | 只在视野内有战斗时推；增量编码；每个世界的推送有上限 |
| Caddy 压缩攒包 | R0 实测；必要时把推送路径排除在 `encode` 之外 |
| 大陆访问 Cloudflare 的物理延迟 | 本方案让延迟只体现在「伤害数字晚到」与「别人延后 100 ms」；如仍不满意，再评估 Cloudflare 付费加速 |

## 11. 实施记录（2026-10-04）

### R0 实测（线上，开启前）
| 位置 | 快照到达间隔 p50 | p95 | 结论 |
|---|---|---|---|
| 源站直连（localhost:3003） | 251 ms | 299 ms | 每秒 4 帧，稳定 |
| 经 Caddy（含 `encode zstd gzip`） | 251 ms | 253 ms | **Caddy 不攒包**，不用改 Caddyfile |
| 经 Cloudflare（开发机） | 248 ms | **805 ms** | Cloudflare 这一跳抖动明显（推送会挤成一批到达） |

开发机复用连接的往返约 0.4 秒，偶尔 0.8～1.7 秒（Cloudflare 走的是 SJC 节点）。结论与方案一致：自己的操作必须本地先走，别人的位置要缓冲后播放。

### 本地验收
- 自动化：`test/realtime.test.ts`（位置校验、异常退回、对空出招、判定区域、躲闪、弹道、延迟补偿、WebSocket 帧解析、票据与实时通道），全部测试 398 个通过。
- 浏览器（本地）：按键到本地位置变化约 150 ms（大部分是测试工具自身的往返）；走动后本地与服务器位置一致、没有回弹；战斗姿态出现准星，鼠标瞄准、左键攻击打中纸扎人；敌人蓄力时地上有红色预警；调试面板显示 WebSocket、战斗通道 15 帧 / 秒。

### 和方案的出入
- 战斗通道没有做「只发变化的字段」：一帧只有参战单位的 `[id, x, y, hp]`，十个单位约 0.4 KB，每秒 15 帧约 6 KB/s，已在目标以内。
- 后台概览的「网络」卡片没有做，统计先放在 `/healthz`。
- 闪避仍由服务器执行（客户端看到 pv 变化后对齐），没有在本地预测。

## 12. 过图的修复（2026-10-04）

线上反馈：走到地图边界会传到下一张地图，又闪回原来的地图。原因是三个问题叠加：

| 问题 | 原因 | 修复 |
|---|---|---|
| 来回传送（与 CDN 无关） | 相邻地图的路口成对：落点正好是「回去」那条路口的起点，下一次上报离它不到 1 格，又被送回 | **落点保护**：换图后离开落点 1.5 格之前不触发路口；兜底的自动换图只在「朝路口走」时触发 |
| 闪回旧地图（CDN 放大） | 换图回执走 WebSocket、快照走 SSE，经 Cloudflare 后乱序（快照间隔 p95 805 ms）；本地只看「版本号不同」，被换图之前生成的旧快照拉回 | **版本号只进不退**：只采用比本地新的快照 |
| 过图后回弹（CDN 放大） | 往返期间发出的旧上报被服务器判「版本号过期」，回执把位置拉回落点 | 上报带**序号**，回执带回序号与 `stale`；比最近一次以服务器为准更早的回执、已知新版本的过期回执一律丢掉 |
| 过图要等一个往返 | 本地走到边缘停住，等服务器回执才切图 | **本地预判过图**：服务器下发路口（`init.links`、`links` 事件）；客户端走到路口立即切到对面并上报 `via`，服务器校验路口、位置、对面地图后换图并回执新版本号；确认前暂停上报，失败或 3 秒超时以服务器为准；预判期间若快照先带来新版本号，只收下版本号、不往回扯 |

另外：换图的那一帧快照还停在旧地图上时，自己的化身按本地的地图判断要不要画（之前会消失一帧）。

验证：`test/realtime.test.ts`（落点保护、朝向、预判校验、过期回执）、`test/localmove.test.ts`（预判过图、确认前不上报、旧快照与过期回执不闪回 / 不回弹）；浏览器在 300 ms 模拟延迟下从混沌走进大地：视图只切换 1 次，轨迹连续，本地与服务器位置一致。
