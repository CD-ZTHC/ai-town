# 地图演变：建筑的一生、地形改造与地图扩张 —— 设计方案

> 状态：设计已确认（2026-09-27，决策见 §11）。尚未实施。
> 相关：[ai-world-evolution.md](ai-world-evolution.md) §5.3 世界架构师、§6.4 世界改造与扩张；[multi-world.md](multi-world.md) §3.2 语义布局 + 确定性生成器、§8 决策权；人员流动（`server/story/migration.js`）。

## 0. 一句话概括

让地图像真实的小镇一样随时间变化：建筑可以**停业、改建、破败、拆除**，空出来的地可以重新利用；可以**修路、架桥、种树、清地**；地方不够时，主地图可以**向任意方向扩展**到 96×64，再往外就长出**相邻的区域**（城东、城西……），走到地图边缘就能走过去；也可以**开辟远处的新区域**。拆除要经过**居民投票与住户同意**。所有变化仍然是可校验、可重放、可撤销的 WorldOp，由需求驱动（有人没地方住、架构师屡次找不到空地、建筑长期没人用），而不是随机发生。

## 1. 现状

### 1.1 已有的能力

| 能力 | 实现 | 谁能用 |
| --- | --- | --- |
| 新增建筑 | `addBuilding`（`server/kernel/ops.js`）；架构师只说「靠近哪里、多大」，`findPlacement` 找位置，`checkPlacement` 以新建筑重建地图校验占地、入口、站位 | 架构师（小改）；施工插件搭脚手架、排工期 |
| 新区域 | `addRegion`（语义布局，layout-v1 落地，默认关闭）、`linkRegions`（打开 / 封闭） | 只有管理员与剧情弧；不在 `ARCHITECT_OPS` 里 |
| 区域开关 | `openRegion`（世界标记 `region_<id>`） | 剧情弧、管理员 |
| 撤销 | 提案撤销 → `revertOps` → `rebuildSpec` 重放 | owner / 管理员 |

地图生成的关键约定：**基础地图由生成器确定性地展开**（云溪镇 `yunxi-v1` 逐格固定，其他世界 `layout-v1`），运行中新增的建筑带 `added: true`，**在基础生成之后叠加**（清理树木、开辟小路、再做一次连通性过滤）。这保证了新增建筑不会改变原地图的随机序列。

### 1.2 缺少的

1. **只能加，不能减**：没有拆除、停业、改建、破败；建筑一旦出现就永远在那里。新增建筑上限 12 座之后，世界的建设就停了。
2. **地形不能改**：不能修路、架桥、清地、种树；`findPlacement` 只能在现成的空地上找位置，找不到就失败。
3. **地图不能长大**：云溪镇是固定的 64×44；创世世界按区域数估算尺寸之后也固定不变。空地用完后，架构师只会反复报「附近没有足够大的空地」。
4. **新区域只有剧情能开**：架构师不能提议开辟新区域；区域之间只有一个渡口（每个区域一个 `gate`，所有跨区域行走都经过主地图的同一个点）。
5. **与人员流动脱节**：新人要住处时只能挤进已有的房子（每处最多 3 人）；有人长期离开后房子空着，也不会有人提议把它改作他用。

### 1.3 顺带发现的写死内容（与多世界不符）

- `server/sim/regions.js` 的 `openRegion` 日志写死「月之渡口」「向小镇敞开」，`seedMoonRumors` 只针对暗月界。
- `server/sim/movement.js` 跨区域行走时的动作写死「经月之渡口」。
- `public/index.html` 的区域切换按钮写死「🌗 去暗月界看看」。

这些在 §5.3 里一并改为读区域数据。

## 2. 原则

1. **基础生成不变，变化是叠加层**。基础地图（含世界包里的建筑）照旧按生成器展开；拆除、改建、地形编辑、扩展都是**按操作顺序依次叠加**在基础地图上的编辑。这样云溪镇的基础瓦片、随机序列永远不变，回放测试可以继续逐帧比对。
2. **AI 不写坐标**。和 `addBuilding` 一样，AI 只描述意图（「把旧仓库拆了」「从农场修一条路到码头」「往东扩一片果园」），坐标与路径由求解器给出，并在应用前完整校验。
3. **没有人会无家可归**。这是「非致死原则」在地图上的延伸：拆除住处必须同时给出搬迁去处；搬不走就不能拆。
4. **引用不能悬空**。任何被拆除的地点，所有引用它的地方（住处、工作地、节日地点、规则触发地点、剧情、出生点、路口……）要么在同一个操作里改指向，要么这个操作不能执行。
5. **居民说了算**。拆除要经过议事会与居民投票，住户（当事人）的意愿有分量（§3.4）。
6. **可撤销**。拆除与扩展都走提案与决策队列，撤销就是从操作历史里移除它再重放；被拆的建筑、搬走的居民随之恢复。
7. **需求驱动，节奏受控**。变化来自具体的需求信号（§6.1），每天有配额，刚建好的建筑有保护期，拆除要经过居民议事。

## 3. 建筑的一生

### 3.1 状态

在规格的建筑上增加 `state` 字段（缺省为 `open`）：

| 状态 | 画面 | 能否进入 | 能否住人 / 工作 | 常见来由 |
| --- | --- | --- | --- | --- |
| `open` 营业 / 使用中 | 正常 | 能 | 能 | 默认 |
| `closed` 停业 / 闲置 | 门窗紧闭、招牌摘下、无夜灯 | 不能（只到门口） | 住处可以，工作地不行 | 店主出门远行、长期没人用、剧情需要 |
| `damaged` 受损 | 屋顶破洞、脚手架 | 不能 | 住户暂住别处 | 剧情（暴风、裂隙侵蚀）；**不是死亡或伤害**，是可以修的麻烦 |
| `ruin` 废墟 | 断墙、瓦砾、杂草（仍占地、仍挡路） | 能到附近（户外地点） | 不能 | 长期受损没人修、拆到一半、剧情 |

再加上 `removed`（已拆除）：建筑从地图上消失，占地变成**空地**（泥土地块 + 零星杂草），原地点不再存在。空地可以被新建筑使用。

### 3.2 操作

| WorldOp | 参数（示意） | 级别 | 说明 |
| --- | --- | --- | --- |
| `setBuildingState` | `{ id, state: open/closed/damaged/ruin, reason }` | 小改（`ruin` 为大改） | 只改状态，不动占地 |
| `renovateBuilding` | `{ id, name?, kind?, desc?, emoji?, style?, public? }` | 小改 | **改建 / 换用途**：占地不变，名字、类型、外观、公开性可以变（空房子改成客栈、旧仓库改成图书角）；地点 id 不变，所有引用自然保留 |
| `removeBuilding` | `{ id, remap: { residents, workers, location } }` | 大改 | 拆除：建筑消失，留下空地；`remap` 在同一个操作里把所有引用改指向（§3.3） |
| `restoreBuilding` | `{ id }` | 小改 | `closed / damaged / ruin → open`（修好了、重新开张） |

为什么「改建」单独成一个操作：大多数「这房子没用了」的场景，改建比拆了再建更自然，而且不用处理引用、不用重新选址，风险最低。架构师的提示词里会优先建议改建。

### 3.3 拆除的连带影响（依赖检查）

新增一个纯函数 `impactOf(spec, runtime, buildingId)`，列出所有引用这座建筑（及其地点 id）的地方：

| 引用 | 位置 | 拆除时的处理 |
| --- | --- | --- |
| 住在这里的人 | `personas[].home` | **必须**给出 `remap.residents`（另一座能住人的建筑）；目标住处按人员流动的规则检查容量（每处最多 3 人） |
| 在这里工作的人 | `personas[].work` | 必须给出 `remap.workers`（任何地点） |
| 日历活动的地点 | `calendar.events[].location` | 必须给出 `remap.location` |
| 规则的 `enter` 触发地点 | `rules[].when.enter` | 同上 `remap.location` |
| **进行中的**剧情弧、未回收的剧情线程里写到的地点 | `arcs`、`threads` | 禁止拆除（剧情落幕、线程回收之后才可以） |
| 世界出生点、区域路口 | `voice.spawn`、`region.gate`、边缘通道 | 必须给出 `remap.location`；路口随之移到新地点 |
| 进行中的施工、已约好的场景 / 约定 | 运行时 | 不阻止，执行时取消并记日志（「原定在 X 的聚会改到了 Y」） |
| 在里面的人、旅人化身 | 运行时 | 执行时移到门口 |

**没有「地标」保护**：AI 可以提议拆除任何建筑，包括世界包里的基础建筑（云溪镇的咖啡馆、图书馆也一样）。约束来自两处：上表的引用检查，以及 §3.4 的居民投票与住户同意。

`removeBuilding` 的 `check` 调用 `impactOf`：必须处理的引用没有给 `remap`，就返回清楚的错误（「林家小屋还住着 2 个人，需要给出搬去哪里」），架构师会带着错误修一轮（沿用现有的修复回合）。`apply` 在规格副本上**原子地**完成：删除建筑与地点、改写所有引用。因为改写在同一个操作里，撤销这个操作时引用也随之恢复。

没有合适的搬迁去处时，架构师可以在同一个补丁里先 `addBuilding` 一座新住处再拆旧的（补丁内的操作本来就按顺序在副本上试应用）。

### 3.4 拆除的议事：居民投票与住户同意

拆除（以及把建筑变成废墟的 `setBuildingState(ruin)`）不是架构师或导演一个人说了算，要经过镇上居民的同意。

**当事人**：住在这座建筑里的人（`home`）和在这里工作的人（`work`）。其余在场的居民（不含生物、出门在外的人）是**投票人**。

**流程**：

1. **提案**：架构师产出拆除补丁（含搬迁去处），设定考据通过后，提案进入「议事中」。
2. **议事会**：导演在当天或第二天安排一场议事场景（沿用多人场景 `scene`），地点是最近的公共地点，参加者是当事人 + 最多 4 位与这座建筑关系最深的居民。场景的对话进入这些人的记忆，让表态有来由，而不是凭空投票。
3. **表态**：议事会结束后，调用一次模型（label「居民议事」，P2 叙事级），把每位居民的性格、与当事人的关系、关于这座建筑的记忆、议事会上说过的话交给它，输出每个人的 `yes / no` 和一句理由（≤30 字）。当事人单独给出「同意 / 不同意搬走」。在场的旅人可以投票，但只作参考，不计入结果。
4. **判定**：

| 当事人 | 投票人 | 结果 |
| --- | --- | --- |
| 全部同意 | 过半数同意 | **通过** |
| 有人不同意 | **全票**同意 | **通过**（当事人被说服不了，但全镇都认为该拆） |
| 有人不同意 | 不是全票 | **否决** |
| 任意 | 过半数反对 | **否决** |

   没有当事人的建筑（空置的房子、无人工作的仓库）只看投票人过半数。
5. **终审**：通过之后仍然交给终审人（用户世界 owner，官方世界管理员；超时交给 AI 裁决官），终审人可以否决，**不能**推翻居民的否决。否决的提案 10 个游戏日内不能对同一座建筑再提。
6. **施工与落地**（§3.5）。

**当事人的重要记忆**：拆除落地时，每位当事人得到一条**重要记忆**（importance 9，反思、日记、对话检索时优先想起）：

- 当事人同意的：记住离开的原因和告别（「我在林家小屋住了二十年。大家商量好要在这里修一条通往码头的路，我答应了。搬走那天我在门口站了很久。」）。
- 当事人不同意、被全票通过的：记住自己的不舍和全镇的决定（importance 9），心情变为失落，持续一天；对投了赞成票、且议事会上说服过自己的人，关系备注里记下这件事（好感不直接扣减，交给之后的相处）；自动生成一个剧情线程「{名字}的旧居」，导演可以之后安排和解、纪念或补偿的故事。
- 两种情况都会写一条正典，记忆和线程的文字由「居民议事」那次调用一并给出，不额外调用模型。

**为什么这样判定**：住户的意愿很重要，但不应让一个人永远卡住全镇的决定；反过来，只要有一位邻居站在住户这边，就不拆。这让拆除成为一件有分量、有故事的事。

### 3.5 施工与叙事

- **拆除也要施工**：`construction` 插件接管带 `removeBuilding` 的提案，和新建一样搭脚手架、给居民排上「拆除：旧仓库」的日程、按工期完工后才真正落地。拆到一半被撤销，建筑保持原样。
- **居民会记得**：拆除落地时，当事人得到重要记忆（§3.4），其他和它有关系的居民各得一条普通记忆（「旧仓库拆了，小时候常在那里躲雨」）；自动写一条正典（「第 N 天，旧仓库被拆除，原址……」），让之后的对话和日报能提到「以前那里是……」。
- **废墟是故事素材**：`ruin` 的地点仍是户外可去的地方，导演可以在那里安排场景；架构师可以提议把废墟修复（`restoreBuilding`）或清走（`removeBuilding`）。

### 3.6 与人员流动的联动

- 新人找不到住处（所有住处满员）→ 给架构师一个意图「为新来的人盖 / 改一处住处」（每天最多一次）。
- 有人长期出门、或定居后搬走，某座住宅空置超过 N 天 → 记为需求信号「闲置建筑」，架构师可以提议改建为别的用途。
- 人员流动选住处时跳过 `closed / damaged / ruin` 的建筑。

## 4. 地形改造

地形编辑同样是叠加层，按操作顺序在基础地图之后应用。AI 只给语义参数，求解器落地。

| WorldOp | 参数（示意） | 级别 | 求解与校验 |
| --- | --- | --- | --- |
| `addPath` | `{ from: 地点id, to: 地点id, surface: path/dirt/plaza }` | 小改 | 用现有寻路（把草地、花地、可移除的树视为高代价可通行）求一条路，沿途铺路面、移除挡路的树丛；遇水时自动转为架桥（仅当水面宽度 ≤ 4，否则失败） |
| `addBridge` | `{ near: 地点id, across: water }` | 大改 | 在附近找最窄的一段水面，铺 `BRIDGE` |
| `clearArea` | `{ near, w, h }` | 小改 | 清掉树木 / 灌木 / 石头，留下草地（为以后建房腾地方） |
| `plantGrove` | `{ near, w, h, trees: oak/pine/sakura }` | 小改 | 只在空草地种；不能挡住任何入口与站位（与 `checkPlacement` 相同的站位不减少校验） |
| `addOutdoorPlace` | `{ id, kind: garden/orchard/market/…, name, near }` | 小改 | 新的户外地点（`OUTDOOR_KINDS`），用 layout-v1 的户外笔刷画在找到的空地上 |

每个地形操作应用后都要满足：所有建筑入口可达、所有地点的可达站位不减少（`addPath`、`clearArea` 只会让可达区域变大，天然满足）。地形操作的数量上限与建筑合计计算（§6.3）。

**不做的**：任意改水域形状、挖湖填湖、改变地貌（biome）。这些改动会让基础生成的装饰分布整体失效，收益不值得复杂度。

## 5. 地图扩张

两层：**主地图在 96×64 以内向任意方向长大**；再往外，就在那一侧**长出一张相邻的地图**（城东、城西、城北……），走到边缘就能走过去。另外保留「远处的新区域」（北山、异界），经路口往返。

### 5.1 边缘扩展：任意方向，最大 96×64

**操作** `expandMap`（大改）：

```jsonc
{ "op": "expandMap", "args": {
    "region": "town",           // 默认主地图；相邻区域也可以扩展
    "side": "west",             // north / south / east / west
    "by": 12,                   // 8~24 格；扩展后不能超过 96×64
    "biome": "meadow",
    "name": "西街",
    "places": [                  // 与 layout-v1 区域块相同的语义地点，最多 6 个
      { "id": "orchard_west", "kind": "orchard", "name": "西坡果园" },
      { "id": "inn", "kind": "inn", "name": "旅人客栈" } ] } }
```

**向西、向北扩展会让坐标平移**。地图坐标以左上角为原点，向西扩 12 格，原来的 (0,0) 就变成 (12,0)。处理办法是让「平移」成为操作本身的一部分：

1. **规格里的坐标**：区域记录累计偏移 `offset: { x, y }`。`expandMap` 的 `apply` 在规格副本上把该区域所有坐标（`added` 建筑的 x/y、地形编辑的格子、已有扩展块的位置）加上位移。因为它就是操作历史里的一步，重放时自然得到同样的结果。
2. **基础地图**：生成器照旧在原尺寸里生成基础地图（云溪镇逐格不变），再整体贴到放大后的画布的 `offset` 位置。
3. **运行时状态**：操作落地的那一刻，小镇把该区域内的一切运行时坐标平移：居民的位置、路径、目的地；施工现场、构筑物、生物、裂隙；旅人化身；待落地提案里的选址。之后存档保存的就是平移后的坐标，与重放得到的规格一致。
4. **不受影响的**：日程、约定、场景都记的是地点 id，不是坐标；记忆是文本。
5. **快照与回溯**：每个快照保存自己时刻的规格操作历史与运行时坐标，二者一致；回溯到扩展之前的快照就是回到旧的地图，没有额外处理。
6. **前端**：收到 `worldmap` 事件时如果带 `shift: { x, y }`，镜头、小地图、正在播放的动画位置一起平移，画面不跳。

扩展之后仍然校验：所有旧地点的可达站位不减少、新地点至少有一个可达站位、接缝两侧有路（把原地图边缘上的道路延伸进来；边缘没有道路时，从新块的中心向最近的可走格开一条小路）。云溪镇东南是镜湖、北边是山溪源头，扩展块的笔刷在接缝一侧用 2 格的过渡带（沙地 / 草地）衔接。

**为什么是 96×64**：前端把静态地形预渲染到一张离屏画布（`TS = 32`），96×64 格是 3072×2048 像素、约 25 MB，手机上可以接受；寻路是全图 A*，6144 格没有性能问题。再大的世界用相邻地图（§5.2）拼起来，每张图各自在上限以内。

### 5.2 相邻地图：城东、城西……

当主地图在某个方向上已经到了上限（宽到 96 或高到 64），再往那边扩展就**新建一张相邻的地图**：

```jsonc
{ "op": "addAdjacentRegion", "args": {
    "id": "chengdong", "name": "城东", "from": "town", "side": "east",
    "size": [48, 64],            // 与接壤边等长的一边自动对齐，另一边 32~96
    "biome": "village",
    "places": [ { "id": "east_market", "kind": "market", "name": "东市" }, ... ] } }
```

- **边缘通道**：两张地图接壤的边上，每条跨过边界的道路形成一个**通道**（至少 1 个、最多 3 个），两侧位置对齐。居民走到主地图东边缘的通道，就出现在城东西边缘对应的位置。求解时新地图的道路从这些通道开始铺，所以两边的路是接上的。
- **行走**：`navigate` 的跨区域逻辑从「走到唯一的渡口」改为「按区域图求最短的区域路线（经过哪些相邻地图），逐段走到对应的通道」。城东、城西相邻于主地图，城东再往东还可以有「东郊」，区域图最多 6 个区域（沿用上限）。
- **默认开放**：相邻地图是镇子的一部分，建成即开放，不需要 `linkRegions`；远处的新区域（§5.3）仍默认关闭。
- **前端**：
  - 观察模式：顶栏的区域切换改为一个小菜单（城中 / 城东 / 城西 / 远处的区域），选中后镜头切过去。
  - 沉浸模式：镜头跟随的居民跨过边缘时，画面顺着方向滑到相邻地图。
  - 游戏模式：旅人化身走到通道就进入相邻地图。
  - 小地图显示区域拼图：当前地图高亮，相邻地图画成灰色轮廓。
- **主地图的名字**：出现第一张相邻地图时，主地图在界面上的名字从「小镇」变成「城中」一类的称呼（由架构师在同一个补丁里给出，存为 `region.name`）。
- 相邻地图本身也可以用 `expandMap` 继续长大，直到它自己的 96×64。

### 5.3 远处的新区域：开放给架构师

适用于不接壤的地方：北山、河对岸的村子、森林深处、异界。已有 `addRegion` / `linkRegions`，本方案要补的是：

1. **架构师可以提议**：`addRegion` 加入架构师可用的操作，级别为大改（owner 终审）；必须同时带一个 `linkRegions`，否则开出来的区域没人去得了。
2. **每条连接一个路口**：现在每个区域只有一个 `gate`，所有跨区域行走都从主地图的同一个点出发。改为：`linkRegions` 在两边各生成一个「路口」地点（例如「北山山口」），行走时走向**目的区域对应的路口**。暗月界保留现在的渡口作为它的路口，行为不变。
3. 远处区域与相邻地图共用区域图与路线求解，只是连接方式不同（路口是点，相邻是边）。

### 5.4 去掉区域相关的写死内容

- 区域的显示名、路口名、开放时的旁白来自区域数据：`region.name`、`link.gateName`、`region.openText`（缺省为「通往「{name}」的路打通了」）。
- 跨区域行走的动作文字为「前往{地点}（经{路口或通道名}）」。
- 区域切换按钮改为 §5.2 的小菜单。
- `seedMoonRumors` 变为通用的「区域开放传闻」：区域可以带 `rumors` 字段；没有时根据区域里的地点生成一两句（不调用模型）。暗月界把现在的三句传闻写进它的区域数据。

## 6. 谁来提议、谁来决定、节奏

### 6.1 需求信号（驱动架构师，而不是随机）

在世界状态里维护一张「地图压力表」，每个游戏日计算一次，写进架构师与导演的提示词：

| 信号 | 计算 | 引出的提议 |
| --- | --- | --- |
| 空地紧张 | 最近 N 次 `findPlacement` 失败次数；各地图可建空地占比 | 清地、扩展地图；到上限后新建相邻地图 |
| 住处紧张 | 人员流动找住处时满员的次数；人均住处 | 新建 / 改建住处 |
| 闲置建筑 | 住宅无人居住、工作地点无人工作、公共建筑 N 天无人到访（需要新增按地点、按天的到访计数，在已有的 `agent.arrive` 钩子里累加） | 改建、停业、拆除 |
| 破败 | `damaged` / `ruin` 持续天数 | 修复或清除 |
| 走得远 | 居民日常往返的平均路程（寻路长度）显著变长 | 修路、架桥 |

压力表同时显示在「🔨 建设」面板里，让玩家也能看到「镇子为什么想扩张」。

### 6.2 审批级别

| 操作 | 级别 | 流程 |
| --- | --- | --- |
| `setBuildingState`（closed / damaged）、`restoreBuilding`、`renovateBuilding`、`addPath`、`clearArea`、`plantGrove`、`addOutdoorPlace` | 小改 | 沿用现有规则（不需终审时自动通过，否则征求意见 + 终审） |
| `removeBuilding`、`setBuildingState(ruin)` | 大改 | **议事会 + 居民投票 + 当事人同意（§3.4）**，通过后终审（用户世界 owner、官方世界管理员，超时交给 AI 裁决官） |
| `addBridge`、`expandMap`、`addAdjacentRegion`、`addRegion` + `linkRegions` | 大改 | 征求意见 + 终审（与现在的大改相同） |

### 6.3 节奏与上限

- **每天**：大改最多 1 个（沿用现有的 `DAILY_QUOTA`）；拆除每 3 个游戏日最多 1 次；扩展与新建相邻地图每 7 个游戏日最多 1 次。
- **保护期**：建成不满 7 个游戏日的建筑不能拆除（避免建了就拆的反复）；居民否决过的建筑 10 个游戏日内不能再提。
- **总量**：取消「新增建筑最多 12 座」的硬上限，改为「每张地图上的建筑数 ≤ 地图面积 / 120」（64×44 约 23 座，96×64 约 51 座）；每张地图的地形操作合计 ≤ 40 个；区域合计 ≤ 6 个。

### 6.4 撤销

所有新操作都经由提案，撤销沿用 `undo → revertOps → rebuildSpec`：

- 撤销拆除：建筑回来、住户与引用恢复原样（因为改写在同一个操作里）。
- 撤销之后，后续依赖它的操作（例如在空地上新建的房子与原建筑重叠）在重放中会被跳过；撤销前先用同样的重放在副本上试算，把会被连带跳过的提案列给终审人确认（「撤销这次拆除，会同时取消在原址新建的『旅人客栈』，确定吗？」）。
- 撤销扩展或相邻地图：里面的建筑、地点一起消失，向西 / 向北的平移也随之撤回（运行时坐标反向平移）；住在里面的居民按拆除的规则需要去处，找不到就不允许撤销（提示先把人搬走）。
- 撤销拆除不需要再投票；当事人的重要记忆保留（那段经历确实发生过），另加一条「后来决定不拆了」的记忆。

## 7. 数据与代码改动

### 7.1 规格

```jsonc
// buildings[] 新增字段
{ "id": "warehouse", "state": "open", "builtDay": 12, "removed": false, "vetoedUntil": null }
// 区域新增：累计偏移、扩展块、地形编辑、相邻关系（都按操作顺序追加，生成器按顺序叠加）
{ "id": "town", "name": "城中", "size": [96, 56], "offset": { "x": 12, "y": 0 },
  "extensions": [{ "side": "west", "by": 12, "biome": "meadow", "name": "西街", "places": [...], "seed": 311 }],
  "edits": [{ "kind": "path", "cells": [[40, 12], ...], "surface": "dirt" }, { "kind": "clear", "rect": {...} }],
  "neighbors": { "east": { "region": "chengdong", "passages": [{ "y": 15 }, { "y": 30 }] } } }
```

- `removeBuilding` 之后建筑并不从数组里删除，而是标记 `removed: true`：生成器仍用它参与基础生成（保证基础随机序列不变），在叠加阶段把它变成空地。新增建筑（`added`）被拆除时可以直接删除。
- `offset` 只由 `expandMap` 改变；基础生成的坐标系不变，贴图时加上偏移。
- `edits` 里保存的是**求解后的结果**（具体格子），不是意图，重放时不再求解，保证确定性。`addBuilding` 保存坐标也是同样的道理。
- 规格校验（`validateSpec`）补充：引用不能指向已拆除的建筑；`state` 取值；扩展后的尺寸上限。

### 7.2 生成器的叠加顺序

两个生成器（`yunxi-v1`、`layout-v1`）共用一段叠加代码（现在两边各有一份几乎相同的「叠加新增建筑」，顺便合并）：

```
基础生成（不变，原尺寸）
→ 贴到放大后画布的 offset 位置
→ 扩展块（按顺序）：在块内布局与笔刷、接缝
→ 拆除：removed 的基础建筑 → 解除阻挡、地块改为泥地空地、去掉地点
→ 状态：ruin → 换成废墟物体（仍阻挡）；closed / damaged 只影响画面与可进入性
→ 地形编辑（按顺序）
→ 新增建筑（按顺序，沿用现有校验）
→ 边缘通道（相邻地图）
→ 连通性过滤（从中心出发的可达性，丢弃不可达站位；所有通道、路口必须可达）
```

## 10. 风险

| 风险 | 应对 |
| --- | --- |
| 改生成器导致云溪镇地图变化 | 基础生成一行不动；叠加层单独一段；地图指纹测试护航 |
| 向西 / 向北平移时漏掉某类运行时坐标（人卡在墙里、施工现场错位） | 平移集中在一个函数里，列出所有带坐标的运行时状态；测试逐类检查；平移后对所有居民做一次「是否站在可走格上」的校验，不在的移到最近的可走格 |
| AI 频繁拆建，世界「不稳定」 | 议事与全票规则本身就是强约束；保护期、否决冷却、每 3 天最多一次拆除；优先改建 |
| 「居民议事」一次调用决定所有人的票，可能千篇一律 | 提示词带上每个人与当事人的关系、关于这座建筑的记忆和议事会的发言；要求每人一句理由；票型全部相同的情况会被记录，便于观察 |
| 拆除让居民的记忆、约定指向不存在的地点 | 记忆是文本，不影响运行；约定与场景在执行拆除时改期或取消并记日志；`resolveLoc` 已有兜底（找不到时回家） |
| 撤销的连锁反应 | 撤销前在副本上试算并列出会被连带跳过的提案 |
| 相邻地图让跨区域行走变长、变慢 | 区域最多 6 个；路线按区域图求最短；日程规划时把跨区域路程计入时间 |
| 扩展接缝不自然（尤其云溪镇的湖边与溪流） | 接缝用 2 格过渡带；扩展块的布局避开接缝两格；溪流、湖泊不越过接缝 |

## 11. 已确认的决策（2026-09-27）

1. **AI 可以拆除**：没有地标保护，基础建筑也可以拆；约束来自引用检查（§3.3）与居民议事（§3.4）。
2. **任意方向扩展**：向西、向北扩展时，平移作为操作的一部分（§5.1）。
3. **主地图上限 96×64，再往外用相邻地图**：城东、城西……以边缘通道连接（§5.2）。
4. **保留废墟**这一中间状态（§3.1）。
5. **拆除要居民投票并且住户同意**；住户不同意时，除住户外全票同意也可以拆除，住户得到重要的记忆（§3.4）。

我的理解与补充（实施前可以再调整）：
- 「住户」扩展为**当事人**：住在这里的人和在这里工作的人（拆一家店，店主同样是当事人）。
- 当事人同意时，投票人**过半数**即可；终审人可以否决通过的提案，但不能推翻居民的否决。
- 把建筑变成废墟与拆除走同样的议事流程；修复、停业、改建不需要议事。
