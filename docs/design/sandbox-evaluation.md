# 插件沙箱：更轻的隔离方案评估（重构方案 P9 第三项）

> 状态：评估完成，**建议采用「一个共享沙箱进程 + 每个插件一个 QuickJS-wasm 上下文」**，尚未实施。
> 本文只做评估与方案设计；实施需要单独的 PR（改写 `plugin-host/sandbox/runner.ts` 与 `client.ts`，插件契约不变）。

## 1. 现状与问题

AI 生成的 T2 插件（`plugins/evolved/*/server.js`）现在每个跑在一个独立的 Node 子进程里（`plugin-host/sandbox/client.ts`）：

- Node 权限模型：只能读运行器与插件目录，不能写文件、联网、开子进程、加载原生模块；
- `--disallow-code-generation-from-strings`，堆上限 64MB；
- 不继承环境变量，经 IPC 收发 JSON。

隔离是够的（进程隔离 + 权限模型，两层），但每个插件一个进程太重。P9 第一项已经改为按需启动、空闲回收、全站最多 3 个（`SANDBOX_MAX`），控制住了总量；但插件一多就要频繁启停，2G 的机器上仍然是主要的内存开销之一。

## 2. 实测

在同一台机器上，用同一个「插件」（一个带存储的钩子函数）分别测三种隔离方式。

- 测试环境：macOS arm64，Node v26.10.0，quickjs-emscripten 0.32.0，isolated-vm 7.0.1。
- 测试方法：每种方式建 10 个沙箱，测平均启动时间与进程 RSS 增量；每种方式调用 1000 次，测单次耗时。
- 测试脚本是临时脚本，没有放进仓库。

| | 现在：每插件一个 Node 进程 | QuickJS-wasm | isolated-vm |
| --- | --- | --- | --- |
| 每个沙箱的内存（RSS） | **约 98MB** | **约 1.3MB** | **约 1.1MB** |
| 启动 | 约 90ms | 0.7ms | 1.3ms |
| 单次调用（含序列化） | 0.08ms（IPC） | 0.012ms | 0.005ms |
| 掐断死循环 | 能（杀进程） | 能（中断回调） | 能（`timeout`） |
| 内存上限 | 能（`--max-old-space-size`） | 能（`setMemoryLimit`，超出抛错） | 能（`memoryLimit`，超出销毁 isolate） |
| 能碰到 `process` / `require` / `fetch` | 不能（权限模型） | 不能（解释器里根本没有） | 不能（新 isolate 里没有） |
| 安装 | 无依赖 | 纯 wasm，约 10MB，无需编译 | **原生模块**，要用 node-gyp 编译（本机编译成功） |

注意：

- macOS 的 RSS 偏高，Linux 上 Node 进程一般在 40~60MB。即便如此，两种轻量方案仍有一到两个数量级的差距。
- 单次调用的时间三种方式都可以忽略。现在的瓶颈是内存和启动时间，不是调用速度。

## 3. 两个候选

### 3.1 isolated-vm

**优点**
- 用的是 V8 本身，带 JIT，最快。
- 插件代码不需要任何改动：标准 JS，ES 模块写法照常。

**缺点**
- **和服务器在同一个进程里**。隔离只有 V8 isolate 这一层：一旦出现 V8 的沙箱逃逸漏洞，攻击者直接拿到整个服务器进程（账号库、凭据主密钥都在里面）。现在是进程隔离加权限模型两层，换过去等于去掉一层。
- **原生模块**：
  - 每个 Node 大版本、每个平台都要编译。
  - P1 的部署约定是「生产机上不装依赖、CI 打包」，所以 CI 要按线上平台编译，Node 升级时要一起验证。
  - 本仓库现在没有任何原生依赖。
- 插件跑满一个核时会拖慢同进程的主循环（isolate 在调用线程上执行同步代码）。

### 3.2 QuickJS-wasm（quickjs-emscripten）

**优点**
- 独立的 JS 解释器跑在 wasm 线性内存里，插件代码看到的世界只有宿主显式放进去的函数。
- 内存上限与中断都是解释器内建的。
- 纯 wasm，无需编译，跟着 npm 包走。

**缺点**
- 没有 JIT，算得比 V8 慢（对插件这种「收到事件 → 算几行 → 返回」的负载，实测仍然是 0.01ms 级）。
- 是另一个 JS 引擎：极少数新语法或内建对象可能不支持。要在插件生成时就用 QuickJS 跑一遍插件自带的测试，把不兼容的挡在门外。
- 宿主接口要逐个桥接（见第 5 节）。

## 4. 建议：共享沙箱进程 + 每插件一个 QuickJS 上下文

两层隔离都保留，内存从「每插件约 98MB」变成「全站约 100MB + 每插件约 1.3MB」：

```
小镇服务器 ──IPC(JSON)──▶ 沙箱进程（1 个，Node 权限模型，同现在的限制）
                              ├─ QuickJS 上下文：插件 A（内存上限 16MB，中断回调）
                              ├─ QuickJS 上下文：插件 B
                              └─ …
```

- **第一层**：沙箱进程保持现在的全部限制（权限模型、无环境变量、禁止字符串生成代码、堆上限）。QuickJS 本身被攻破，也只能在这个进程里打转。
- **第二层**：每个插件在自己的 QuickJS 上下文里，彼此之间、和宿主之间只能经桥接函数交换 JSON。
- 进程崩溃时所有插件一起重启（`client.ts` 现有的崩溃重启逻辑），存储每次启动重新读取（P9 第一项已修复）。
- `SANDBOX_MAX` / `SANDBOX_IDLE_MIN` 改为控制上下文；进程本身在没有活跃插件时同样空闲回收。

不选 isolated-vm 的理由：省下的内存和 QuickJS 差不多，却要去掉进程隔离这一层，还要引入原生依赖。这里的插件代码由模型生成、由模型评审，安全边界比性能重要。

## 5. 迁移要做的事

插件契约（`plugin.json` 与 `server.js` 的 `export default function setup(api)`）**不变**，进化引擎生成的插件不用改。

| 接口 | 现在 | QuickJS 下 |
| --- | --- | --- |
| `api.effect / on / route` | 注册函数 | 同样注册在上下文里；宿主按名字调用，参数与结果走 JSON |
| `api.log / overlay` | 写进本次调用的副作用 | 桥接函数，同样只在调用期间有效 |
| `api.store.get / set` | 进程内的对象 | 上下文里的对象；进程启动时由宿主注入 |
| `api.llm(prompt)` | 经 IPC 请宿主调用，返回 Promise | 宿主函数返回 QuickJS 的 Promise（`vm.newPromise`），模型回复到达后 resolve 并执行 `executePendingJobs` |
| 插件目录里的相对 import | 模块加载器限制在插件目录 | `setModuleLoader` 同样只允许插件目录里的文件 |
| 插件自带的测试（`test.js`） | `runPluginTests` 另起进程 | 在 QuickJS 里跑；**进化门禁也改用 QuickJS 跑**，引擎不兼容的插件在生成阶段就被拦下 |

工作量估计：
- `runner.ts` 改写约 200 行；
- `client.ts` 把「每插件一个进程」改为「每插件一个上下文 id」，约 100 行；
- 测试：`test/sandbox.test.ts` 现有的隔离用例全部保留，并补上下文之间互不可见、内存上限、中断的用例。

## 6. 风险

| 风险 | 缓解 |
| --- | --- |
| QuickJS 不支持插件用到的某个语法 | 门禁阶段用 QuickJS 跑插件测试；提示词里约束只用 ES2020 |
| 一个插件把共享进程拖垮（例如大量分配） | 每个上下文有内存上限与中断；进程级仍有堆上限，崩溃后整体重启 |
| quickjs-emscripten 停止维护 | 它只是 QuickJS 的 wasm 封装，可以换成其他封装或自行编译；插件契约不依赖它 |
| 迁移期间出问题 | 设置项切换新旧实现（默认旧实现），灰度一段时间后再切默认值 |
